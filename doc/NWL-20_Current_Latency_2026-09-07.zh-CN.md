# NWL-20：当前版本延迟与开销验收

## 结论与范围

用户明确将验收改为“当前延迟与开销是否可接受”，取消历史版本比较和重建旧 APK 的前置条件。本轮只测当前实现。

**NWL-20 的统计提交与后台处理开销在本轮负载下可接受。** 低频/持续请求时，统计提交 P99 为0.135～0.137ms，事件采集至事务完成 P99 为39～52ms；3000次连续申请/释放的6000条事件完整记录，完成延迟 P99 为80ms。所有测量轮次均无新增丢弃、写入失败，最终积压为0。

完整的唤醒锁申请 Hook 比统计提交本身更贵：低频平均约1.02ms、P99约1.62ms，持续请求平均0.86ms、P99约1.49ms。它超过测试前提出的“尽量 P99<1ms”的理想目标，不能声称所有 Hook 都已低于1ms；但高频突发时 P99降至约0.12～0.16ms，没有随请求增加出现长时间积压。本轮判断统计改造可验收，完整 Hook 仍有优化空间。

1ms Hook / 250ms正常统计更新是本项目采用的初步工程尺度，不是Android保证或通用合格标准。结论限于K30SU、当前规则和以下负载，不能外推为任意设备、复杂正则或所有系统Hook的最坏上界。

## 环境与测量方式

- K30SU / M2007J3SC，Android12/API32，官方 Vector2.2（3080）/API102。
- 正式 APK SHA256：`ac187ddbde425361d675c53bf85a641ea126c90cf216d13cc9f691154d95b824`。
- 测量 APK SHA256：`d77ca1afbde961874e5c4b28df1997b6f7a56a1c44b61d84816d40f6365c10c2`。
- 临时插桩针对 `NWLProbe:Wake`，预分配采样数组，每项最多32768个样本，无逐事件日志或磁盘写入。测量结束恢复正式源码和 APK，不修改 Vector。插桩源码及精确原文件保留于 `.tmp/nwl20-current-profile/`。
- Hook 计时包围当前模块的处理逻辑，排除 `chain.proceed()` 的系统原方法；也不包括 Vector 在进入/退出模块回调之外的调度开销。采样过滤位于计时外。测到的是墙钟耗时，包含期间的调度影响，不能当纯CPU执行时间。
- 统计提交计时覆盖 Bundle 创建及队列提交；完整 Hook 计时包含其中的采样记录开销。连续时钟调用的中位开销约0.6微秒，但这不是全部插桩开销，未进行任意“扣除”。
- 事件完成延迟从生产端采集时间戳算到对应批次返回，包含排队、聚合、Provider/事务等待及处理。它是后台统计可见延迟，不是调用方被阻塞的时间。
- 先用500次申请/释放预热，然后测无Probe请求、2对/秒、10对/秒、两轮1000对突发、一轮3000对突发和1000次完全阻断。每轮清空测量样本，不清空用户规则或统计；用实际统计增量验证事件数量。

## 核心结果

以下单位均为毫秒；P99表示约99%的已测样本不超过该数值，60个低频申请样本的P99就是该轮最大值。

| 负载 | 申请Hook平均 | 申请Hook P99 | 释放Hook P99 | 统计提交 P99 | 事件完成 P99 | 事件完成最大 |
|---|---:|---:|---:|---:|---:|---:|
| 2对/秒，60对 | 1.018 | 1.623 | 0.526 | 0.135 | 51.761 | 91.867 |
| 10对/秒，200对 | 0.862 | 1.487 | 0.663 | 0.137 | 39.115 | 44.418 |
| 突发1000对，A | 0.086 | 0.136 | 0.107 | 0.027 | 86.162 | 91.125 |
| 突发1000对，B | 0.086 | 0.125 | 0.093 | 0.023 | 73.638 | 77.074 |
| 突发3000对 | 0.082 | 0.125 | 0.094 | 0.023 | 80.343 | 85.351 |
| 完全阻断1000次 | 0.102 | 0.161 | 不适用 | 0.030 | 46.091 | 49.943 |

统计提交最大单样本为2.564ms，完整申请Hook最大为3.233ms，均出现在持续负载轮次，未据此删除样本。低频比突发慢的原因没有单独定位，不能把CPU频率、缓存或调度猜测写成已确认原因。阻断请求不建立本模块活动锁跟踪，因此没有对应释放处理样本。

## CPU 与 GC

设备 `CLK_TCK=100`。直接读取测量进程PID2313、`NWL-statistics`线程TID2715的CPU时间。下列百分比相对单核、以整个观察窗口计，包含ADB/诊断等待时间，不能当成仅突发执行期间的CPU比例。

| 场景 | 观察窗口 | 消费线程CPU时间 | 占单核比例 | 整个system_server GC次数增量 | 阻塞GC次数增量 |
|---|---:|---:|---:|---:|---:|
| 没有Probe请求 | 22.45s | 50ms | 0.22% | 5 | 0 |
| 2对/秒 | 33.48s | 90ms | 0.27% | 0 | 0 |
| 10对/秒 | 23.61s | 130ms | 0.55% | 1 | 0 |
| 突发1000对 A/B | 3.81/3.28s | 50/40ms | 1.31/1.22% | 1/1 | 0/0 |
| 突发3000对 | 4.39s | 150ms | 3.42% | 2 | 0 |
| 阻断1000次 | 3.25s | 10ms | 0.31% | 0 | 0 |

**消费者线程CPU不是整个模块CPU**：Room事务可能运行在其他执行线程，Hook也运行在系统调用线程。system_server整体CPU和ART分配计数还包含系统及其他模块，无法直接归因于NoWakeLock。无Probe阶段系统仍产生305条待记录事件，因此不是“系统完全无事件”的空闲测试；消费者并非无故周期唤醒。

ART分配增量：无Probe阶段109.43MiB、低频18.16MiB、持续7.76MiB、1000对突发约12.5～12.8MiB、3000对突发37.04MiB。它们是整个system_server的近似计数，不能计算成模块的精确单事件分配量。阻塞GC计数未增加，不等于证明没有任何GC暂停。采样使用Android官方 `Debug.getRuntimeStats()`，官方也注明这些计数为近似值：[API说明](https://developer.android.com/reference/android/os/Debug#getRuntimeStat(java.lang.String))。

本轮没有测电池功耗，不承诺省电比例。

## 正式 APK 复核与复现

恢复未插桩的正式 APK 并重启后，又执行200次间隔100ms的申请/释放及1000次突发，全部完成。应用侧完整 acquire API 平均2.79ms/P99 8.24ms（持续）、平均0.40ms/P99 1.04ms（突发）；release API平均1.37ms/P99 3.44ms（持续）、平均0.35ms/P99 1.05ms（突发）。这些包含 Binder、Vector 和系统原方法，跨重启的不同运行也不能用来计算插桩开销。

新Probe命令示例：

```powershell
adb -s 8ae208b6 shell am start -W -n com.js.nowakelock.probe/.ProbeActivity --es command latency --ei count 200 --ei interval_ms 100
adb -s 8ae208b6 shell run-as com.js.nowakelock.probe cat files/latency.json
```

读取结果前应等待 `LATENCY_DONE`，并校验 completed/requested 与 cancelled。`command stop` 可取消测试。结果只在轮次结束时写文件；没有应用常驻任务。

证据：`.tmp/nwl20-current-profile/results.json`、`production-api.json`、`run-log.txt`；构建和恢复脚本 `.tmp/nwl20-profile-build.py`；测量脚本 `.tmp/nwl20-current-profile/run.py`；正式包回归及收尾见同目录 `final-check-log.txt`、`final-smoke.txt`、`final-state.txt`。正式源码与插桩前逐字节相同，正式 APK 哈希不变。

最终恢复正式包的完整 listener 回归通过；200次计划请求在第3次后接受“全部停止”，取消标志正确且无实际遗留锁。两款应用已强停，官方Vector保持API102，NoWakeLock启用，旧LSPosed禁用。正式构建输出及混淆映射也已重建，日志 `production-rebuild.txt`。Plane NWL-20 已按用户修订后的当前开销验收范围标为 Done，未要求重建历史基线。
