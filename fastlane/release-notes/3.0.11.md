# NoWakeLock 3.0.11 — Test release / 测试版

**versionCode: 89 · Prerelease · Prepared 2026-09-12**

## 中文

这是旧 Xposed 与官方 API 102 双路径适配的公开测试候选。请通过 GitHub 的 **Pre-release** 渠道发布，暂不作为稳定版推广。

### 更新内容

- 保留原有旧 Xposed 入口，新增独立的官方 API 102 运行路径，适配唤醒锁、闹钟和 Service 拦截。此次兼容目标是原有旧框架与正式 API 102，中间过渡 API 不在支持承诺内。
- API 102 使用官方 Remote Preferences 保存规则，并通过现有 SettingsProvider 通道确认规则实际生效。规则以完整快照原子替换；修改规则无需重启，也不要求 NoWakeLock 应用常驻后台。
- 统计改为有界队列和后台批量写入，减少 Hook 调用中的工作；补充积压、丢弃、失败和时长可靠性诊断。队列过载时会报告统计丢失，不承诺无限负载下无损。
- 支持官方 API 102 模块代码热重载：提供手动更新入口，并启用 APK 更新触发的自动重载。交接规则、统计和正在持有的唤醒锁状态，退出旧监听器和工作线程。
- 模块检查区分规则版本、实际执行的 Hook 构建和恢复状态；同 versionCode 重建时，不再仅凭框架的“已是最新”跳过需要的手动重载。

### 修复

- 修复包含空正则组时规则发布失败、界面已保存但系统未收到新规则的问题。
- 修复统计读取、反序列化或本地缓存写入失败时误清空系统端统计的问题。
- 修复现代 Service 嵌套调用多个重载方法导致一次请求重复计数；启动、绑定和不同用户仍分别统计。
- 修复首次被拦截的唤醒锁导致后续持锁时长虚增的问题，改进重叠持锁和清空统计时的事件处理。
- 修复旧框架阻断 bindService 时返回值错误引起的空指针异常。

### 升级与试用

1. 先导出规则备份。同签名的 v3.x 安装包可以覆盖升级；若从本地调试签名切换到 CI 发布签名，Android 可能拒绝覆盖安装。需要卸载时，请先备份，重新安装后恢复规则。
2. 在框架中启用 NoWakeLock，并确认系统作用域已勾选。从尚不具备热重载回调的旧构建首次迁移时，仍可能需要一次正常重启；单纯关闭再启用模块不能保证替换已进入系统进程的旧 Hook。
3. 后续在已具备热重载能力、框架支持该能力的 API 102 环境中，更新 APK 可自动替换模块代码。Vector 2.2 依赖递增的 versionCode 判断自动更新；同 versionCode 的本地重建可使用模块代码更新按钮。旧框架的 APK 更新仍按原有重启方式生效。
4. 升级后检查模块状态及实际拦截。报告问题时附上设备/Android/框架版本、应用版本、所在 Android 用户、模块检查状态，以及可复现的放行或阻断操作。

### 验证范围与待测项

- 同一实现的前序本地候选 `3.0.10 / 88` 已在 OP13、Android 16、Vector 2.2（API 102）通过手动及 APK 自动重载，保持系统进程和开机状态不变，并验证跨重载持锁和用户 0/10 的唤醒锁、闹钟 listener、Service 启动/绑定放行、阻断、恢复。
- 前序候选通过 120 项单元测试、混淆 release 构建，以及独立 ART 旧入口/102 多次交接夹具。夹具不等于旧框架整机测试；这些真机证据也不等于新 CI 签名产物已经安装验收。
- 当前最终实现仍需补旧框架整机回归、独立 SettingsProvider 进程的 ROM、首次解锁前启动，以及热重载期间同用户重叠持锁、间隔历史和并发规则编辑。最终确认界面的再次点击也待复核。
- K30SU 上曾有普通后台广播闹钟延迟，在禁用模块后也能复现；已通过的 listener 闹钟测试不代表该广播路径全部通过。未将其认定为本版本修复项。

## English

This is a **prerelease** of the legacy Xposed / official API 102 compatibility update. It is intended for testing before a stable rollout.

### Changes and fixes

- Keep the existing legacy entry and add a separate official API 102 runtime for wakelocks, alarms and services. Intermediate API revisions are outside the compatibility target.
- Persist API 102 rules through official Remote Preferences, confirm activation through the existing SettingsProvider channel, and atomically replace complete rule snapshots. Rule changes need no reboot or resident NoWakeLock app.
- Batch statistics in a bounded background queue, with backlog, drop, failure and duration reliability diagnostics. Overload is reported rather than hidden.
- Add official API 102 manual and APK-triggered module code reload, handing over rules, statistics and active wakelocks while retiring old workers and listeners. Module checks verify executing builds and recovery state, including rebuilds with the same versionCode.
- Fix rule publication with empty regex groups, accidental statistics clearing after app-side read/cache failures, duplicate modern Service overload counting, inflated duration after a first blocked wakelock, and legacy bindService blocking return values.

### Upgrading and validation limits

Back up rules before upgrading. Matching v3.x signatures allow an in-place update; a local debug-signed APK may require backup and reinstall when switching to the CI signing key. Enable the module and its system scope in the framework.

An initial upgrade from a build without retirement callbacks may still need one normal reboot. Subsequent upgrades on capable API 102 modules/frameworks can reload automatically. Vector 2.2 requires an increasing versionCode for automatic updates; use the module code update action for same-code rebuilds. Legacy APK updates retain their normal restart requirement. Rule edits remain independent of code reload.

The preceding local `3.0.10 / 88` candidate passed OP13 / Android 16 / Vector 2.2 manual and automatic reload, active wakelock continuity, and user 0/10 allow/block/restore tests for wakelocks, listener alarms and service start/bind. It also passed 120 unit tests, a minified release build and standalone ART entry/handover checks. This is evidence for that candidate, not installation acceptance of the new CI-signed APK.

Remaining device coverage includes the final implementation on a legacy framework, ROMs with a separate SettingsProvider process, startup before first unlock, same-user overlapping locks, interval history and concurrent rule edits during reload, and a final confirmation-screen recheck. Delayed ordinary background broadcast alarms were also reproduced with the module disabled on K30SU; listener alarm tests do not establish full broadcast-path coverage.

Please include device, Android/framework versions, app version, Android user/profile, module check status and reproducible actions in test feedback.

Implementation and validation details: [hot reload](https://github.com/NoWakeLock/NoWakeLock/blob/4b716ad/doc/NWL-22_API102_Hot_Reload_2026-09-12.zh-CN.md), [Service counting](https://github.com/NoWakeLock/NoWakeLock/blob/4b716ad/doc/NWL-23_Service_Overload_Counting_2026-09-12.zh-CN.md).
